# Custom input, actions, and text

[Terminology and reading conventions](01-terminology-and-reading-guide.md).

`InputRouter` normalizes physical events, derives configurable actions, and transports text-service composition/commits. It does not own text shaping, font selection, layout, widgets, or hit testing; those belong to the user interface (UI)/text layer in [25](25-ui-text-and-editor-tools.md).

## 1. Three separate input products

The service never conflates these layers:

| Layer | Data and purpose |
|---|---|
| Physical | Ordered key/button/axis/pointer/wheel/focus/device events with physical control identity and native-source metadata |
| Action | Rebound, context-filtered game/application actions (`Pressed`, `Released`, `Held`, axis values, cancellation reason) derived from physical events |
| Text | IME preedit/composition, committed Unicode text, and composition cancellation delivered to a focused `TextInputSession` |

Raw key transitions are not text. Text is not synthesized from an action binding. An input method editor (IME) composition update does not create a gameplay key press. Text clients may receive the original physical keys independently, but no path delivers the same committed string twice.

## 2. Native sources and capability differences

The core consumes normalized events; concrete sources are explicit:

 * **Windows 11:** Win32 Raw Input (`WM_INPUT`) supplies physical keyboard/mouse data and per-device identity. Register each raw-input device class once per process to a host-owned dispatcher window; Windows routes that class to the most recently registered target, so individual windows/plugins may not re-register it. Window focus and normal Win32 messages scope keyboard/text input; the host routes each raw event to the focused window. The baseline does not request background/sink input. `GameInput` is the preferred standard-gamepad adapter when its documented PC runtime is installed; it supplies device enumeration, timestamped readings, polling/callback operation, and disconnects. Drain its reading history on the host owner thread at every `GameInput`/device wake so intermediate button edges are retained. The baseline does not register Raw Input for gamepad HID, avoiding duplicate delivery. The engine does not also deliver `GameInput` keyboard/mouse if Raw Input owns those devices. Missing `GameInput` reports gamepad capability unavailable; it does not fabricate a device or silently switch application programming interfaces (APIs).
 * **Wayland:** `wl_keyboard` supplies evdev-style key codes, keymap, focus/enter key state, and compositor timestamps only while the surface has keyboard focus. `libxkbcommon` applies the compositor keymap and compose/dead-key state. `wl_pointer` supplies surface-scoped absolute motion/buttons/wheel; there is no global cursor query/warp. `zwp_relative_pointer_v1` plus `zwp_pointer_constraints_v1` are optional for relative capture. When present, expose accelerated and compositor-reported unaccelerated relative deltas separately; the latter is not described as direct hardware data. `Standard` gamepads are discovered separately using udev and `/dev/input/event*` evdev; open only nodes permitted to the current user/seat. `EVIOCSCLOCKID(CLOCK_MONOTONIC)` is requested for evdev timestamps, and device removal/re-addition creates a new generation.
 * **X11 fallback:** Xlib/XInput2 events supply focused-window keyboard/mouse and extension-device data; XKB/libxkbcommon-x11 maps key state. XIM/XIC is used for text input. evdev/udev remains the gamepad source so mapping/hotplug semantics are consistent with Wayland. Server/global pointer behavior is exposed only where X11 actually provides it and is not generalized to Wayland.

The engine reports each capability per window/session/device: `PhysicalKeyboard`, `PhysicalPointer`, `RelativePointer`, `TextCommit`, `TextComposition`, `SurroundingText`, `Gamepad`, `GamepadRumble`, `GlobalPointer`, `RawDeviceIdentity`, and `ClipboardText` are independent. The `InputRouter` does not implement clipboard access; it exposes the host's `ClipboardText` capability, while UI code calls the separate platform service in [15](15-platform-host-and-devices.md) directly. Gameplay input requires no clipboard, while the editor requests the service and visibly disables/reports Paste after a denied or expired user gesture; a new explicit gesture may retry, and failure never becomes a fake empty paste. Version one requires no rumble/force-feedback, touch gestures, or global hooks. Wayland text-input-v3, fractional scale, pointer constraints, raw controller nodes, IME/input method, clipboard selection transfer, and hardware device presence are not guaranteed by all compositors or installations. Failure to acquire seat/device permission is a named `PermissionDenied`/`Unavailable` result.

### Input recipient and clock-domain ownership

`InputRouter` is per recipient, never process-global. Each instance binds at creation to exactly one `InputRecipientKind` (`HostLiveUI` or `SimulationTimeline`) and one nonzero runtime `InputRecipientId`. The ID comes from the private process-wide `Core` `OwnerId` allocator in [03](03-shared-conventions-and-clocks.md); it contains no `HostId`, is never reused, and is not a persistent asset identifier. `Complete` action-state identity is `(InputRecipientId, MapId, ActionId)`; inside one router, maps/actions remain keyed by `(MapId, ActionId)`. Physical, context, input-mask, replay, cursor, and action state are all owned by that router. A router cannot drain, query, or replace another recipient's state.

`HostLiveUI` is one host-clock recipient per native window. It consumes its window's events at the host-control pump in `(HostTimestamp, HostSequence)` order, has no simulation `TickIndex`, and is unaffected by any world's pause or `TimeScale`. A `SimulationTimeline` recipient is bound to exactly one `Core` simulation clock domain and owns its own next-open tick, conversion-segment cursor, and pause state. `Core` exposes only the narrow input-clock contract needed to supply immutable [03](03-shared-conventions-and-clocks.md) wall-to-simulation segments, pause state, and the next open tick. The timeline adapter in `Integration`/`Hosting` implements that contract for one simulation timeline; the `Input` module depends only on `Core` contracts, never on `EngineHost`, a `World` class, or entity-component-system (ECS). Private clock backing may use `TimeProvider`; the input contract does not require callers to pass that implementation object. A headless simulation may own an independent `SimulationTimeline` recipient, but has no native physical route unless it is explicitly fed recorded or injected input.

`One` host-owner `PlatformInputBroker` captures each normalized event once, assigns its `HostTimestamp` and process-wide `HostSequence` once, then fans the immutable envelope to the recipients registered for that source at capture time. Recipient queues hold independent references/copies and cursors; registration changes never replay earlier records, and a recipient never destructively reads a shared queue. The same source event sent to UI and gameplay keeps exactly the same timestamp, sequence, source handle/generation, and native diagnostics. UI receives the event first and returns an event-time `UiInputDisposition` (captured classes and/or per-control consume-lease starts/ends); the broker attaches that disposition to each affected gameplay copy before enqueue. A timeline later applies the copied decision at the event's assigned tick and never consults the UI router's newer state. UI capture of a held control cancels/disarms the affected gameplay binding; captured/consumed up or neutral records are still copied for bookkeeping and release the recipient's disarm. A control routed to a gameplay recipient remains subscribed through its matching up/neutral, device removal, focus reset, or recipient shutdown even if the UI consumes it or window focus changes.

Version 0.1 supports multiple independent window routes: each native window has one `HostLiveUI` recipient and at most one attached `SimulationTimeline` recipient, and a live simulation timeline attaches to at most one native window. Keyboard and pointer input route only to their focused/window recipient pair; no hidden cross-window or global-keyboard route is implied. Text/IME and clipboard remain `HostLiveUI` products. A gamepad is explicitly assigned to one `SimulationTimeline`/`PlayerSlot`; it may also be copied to that window's `HostLiveUI` for navigation only when separately declared. It is never broadcast implicitly to other timelines. Multiple headless timelines remain independent recipients and do not contend for or consume one another's physical-event copies.

Platform native-device state is a live capture mirror only. A simulation recipient derives physical and action state solely by applying its own copied records in its own assigned-tick order; it never samples the current native mirror, another timeline's state, or a later UI state while evaluating an earlier tick. A record assigned to a future tick stays in that recipient's inbox and cannot mutate the earlier tick's controls/actions. Focus/device/resume reconciliation is an explicit new `StateReconciliation` record stamped at the moment the snapshot is observed; it is never backdated to seed a previously assigned tick. Thus one host event can map to different ticks in two timelines with different time-scale/pause segments without sharing physical state or replay cursors.

### Controller normalization

An `InputDeviceHandle` is `(OwnerId, Index, Generation)` and is never a recycled operating system (OS) path or bare index. Disconnect immediately emits a device-removed transition, releases/cancels all controls from that generation, and invalidates its handle. Reconnect is a new generation even if vendor/product/serial match. Persistent profile matching on vendor/product/serial is optional and privacy-sensitive; it never revives an old handle.

`GamepadState` has physical-position buttons `South/East/West/North`, `Dpad`, `Menu/Start/System`, bumpers/triggers, and two sticks; axes are normalized to finite ranges. Linux uses the kernel gamepad specification when a device follows it, supports both digital and analog D-pad/trigger reports, and applies `EVIOCGABS` min/max/flat/fuzz to normalize controls. For each D-pad direction, select its digital button when present, otherwise its analog hat direction; simultaneous duplicate representations produce one canonical state/transition. Device-specific mappings are data profiles, not assumptions about button labels. Unmapped native controls remain diagnosable and are not guessed. Default routing is explicit assignment; unassigned controllers do not trigger a player's actions. `AssignDevice(device, simulationRecipient, playerSlot)` changes the route at that timeline's boundary and emits assignment/loss events to the affected recipient only.

## 3. Timestamping, bounded queues, and tick boundaries

Each broker capture record contains `HostTimestamp` from the private monotonic source, initially injected `TimeProvider.GetTimestamp()`, process-wide `HostSequence` (`long`), source/device/window handle and generation, event kind, physical control/value, optional native timestamp plus clock-domain label, and resynchronization flags. [03's clock contract](03-shared-conventions-and-clocks.md#2-four-clocks) owns source-independent domain/conversion rules; neither capture nor recipient APIs expose the backing provider. The broker assigns the timestamp/sequence once at observation; every recipient copy retains that exact identity. A simulation recipient adds its own `AssignedTick`/`Late` metadata; the shared capture record is never rewritten for another timeline. `HostSequence` exhaustion faults the capture broker rather than wrapping or restarting a recipient stream. Native time is diagnostic only; it is not compared directly to UTC or used to order normalized events.

`Cross`-source canonical capture order is always `(HostTimestamp, HostSequence)`; equal timestamps retain process-wide sequence order. Native timestamps and clock-domain labels are diagnostic data only in version one. They may be compared for diagnostics within their own source, but they are never calibrated/remapped to reorder canonical events across devices or move an already observed event before another source. A regressing, wrapping, or otherwise invalid native timestamp is marked `TimestampUncertain` and diagnosed without changing host order.

Each `InputRecipient` owns a separate finite inbox/cursor, limited to 4,096 pending recipient records and 256 KiB of UTF-8-equivalent text payload by default; text records route only to `HostLiveUI`. A broker may share immutable capture storage by reference, but each intended recipient is charged against its own budget and acknowledges/drops only its own copy. Keyboard/button edges, committed text, focus, device add/remove, reconciliation, and action-control transitions are never silently coalesced or overwritten. Continuous mouse motion/analog-axis updates may be coalesced independently in a recipient inbox only when adjacent for the same source/control/window and no discrete event lies between them; the coalesced copy retains first/last timestamps, sequence range, and replacement count. Coalescing never changes a press/release/text event.

An overflow belongs to exactly one recipient. That router latches `InputOverflow` with its queue/text capacity, source, and first/last unaccepted `HostSequence`; it cancels its active actions once, clears/disarms uncertain state, marks only its recorder discontinuous, drops/advances only its own unconsumed copies, and requests a new-time `StateReconciliation` before resuming affected controls. The broker continues fanout and sequence identity for all other recipients. The host owner calls each router's `ServiceHostControlBoundary` on every wall-pump iteration before deciding whether any world tick is admitted, including while paused, at `TimeScale = 0`, or with no accumulated tick. Tick admission also gates that recipient's latched-overflow sources, so uncertain records cannot leak into its gameplay before recovery. If `HostLiveUI` overflows or is disposed, its own records/leases are cleared and a sequenced `UiDispositionReset` is sent to its attached gameplay recipient; the game recipient applies that explicit mask reset to its own state, without clearing its queue or affecting another window/timeline.

Pausing a `SimulationTimeline` cancels its active actions at that timeline's host-control boundary, discards and counts only that recipient's pending gameplay copies, and suspends new gameplay fanout to it until resume. `HostLiveUI` and other timelines continue normally. Resume captures a fresh native state snapshot and fans it as a new-time, sequenced `StateReconciliation`; held controls are disarmed, so no paused tap or current native state is backdated into an earlier tick. Disposing a recipient unregisters only its route, emits `Canceled(RecipientDisposed)` for its active actions, and releases only its unread references/cursor; records still awaiting other recipients remain retained. Recorded intentional pause/cancellation/discard boundaries reproduce the defined policy and do not by themselves invalidate `StrictLocal` replay. Disposal is a recorded terminal boundary. Unknown overflow/unreconciled state remains non-certifying; no sibling inbox is silently drained.

Tick assignment uses only the `SimulationTimeline` recipient's immutable per-timeline wall-to-simulation and `TimeScale`/pause conversion segments in [03](03-shared-conventions-and-clocks.md); `InputRouter` does not define a competing conversion. The ideal simulation boundary for tick index `i` is `B(i) = floor((i + 1) * 10000000 / tickRate)` `TimeSpan` ticks of simulation elapsed, using the checked arithmetic in [03](03-shared-conventions-and-clocks.md). At 60 Hz, tick index 0 ends at simulation-elapsed tick 166,666. The host observation timestamp maps to an eligible tick only through that recipient's recorded conversion segment; `B(i)` is not independently treated as a wall-clock deadline. Tick index 0 consumes events observed from host epoch zero through its mapped first boundary inclusive. Later ticks consume that recipient's events whose mapped simulation times fall in `(B(i-1),B(i)]` exactly once. Events exactly on a boundary belong to the tick ending there. The same captured event may map to different ticks in different timelines; no timeline advances another's cursor. Press then release within one tick yields both ordered transitions, `PressedThisTick = true`, `ReleasedThisTick = true`, and final `IsDown = false`. If host observation arrives after that recipient's eligible tick was already consumed, assign its copy to that recipient's next open tick, preserve the original host timestamp/sequence, mark only that copy `Late`, and record the recipient's assigned tick. Replay records recipient identity/kind, the relevant time-scale segment revision, and its assigned tick/sequence. `HostLiveUI` records have no assigned simulation tick. A pause boundary discards that timeline's paused copies; UI and other timelines continue, and resume reconciliation is a new-time record, never buffered gameplay input.

## 4. Physical events, action values, and rebinding

Public pointer/delta/Axis2 values are chapter [06](06-owned-geometry-and-numerics-interchange.md)'s `TerraFX.Numerics.Vector2`, not a base class library (BCL)-specific payload or vector4-sized overlay. Existing finite/range/hysteresis and action signed-zero normalization rules remain unchanged; raw interchange does not perform action processing. `Input` still depends only on `Core`, with `EngineGeometryBinary32Rows2` included in generated metadata/replay identity.

`PhysicalInputEvent` supports key down/up/repeat, pointer button down/up, absolute/relative motion, vertical/horizontal scroll, gamepad button/axis, focus/window enter/leave, device added/removed/assigned, and state reconciliation. A physical key carries a stable USB HID page/usage when mapped plus native scan/key code; both physical-layout-independent and explicitly named logical-key bindings are possible. Unknown native usages remain exposed as opaque backend codes but are not portable configuration identifiers.

Mouse wheel units remain tagged: Windows detents use `delta/120`; Wayland continuous axis values are surface-scale units and optional value 120 is a separate detent signal. No fabricated cross-platform conversion hides the difference. Pointer positions are window-local physical pixels plus the observed content scale; relative deltas remain relative and are not converted to global positions.

An `InputActionMap` is a versioned data contract, not an arbitrary callback graph. Version one has these records:

The field types below describe signed semantic/authoring values where appropriate: schema versions and bounded millisecond counts use `int`, revisions and host/insertion/tick sequences use nonnegative `long`. Live revisions and host/insertion sequences are positive and refuse before `long.MaxValue` exhaustion. [10](10-binary-data-and-authoring-formats.md)'s corresponding `UInt32`/`UInt64` wire kinds/tags remain fixed, with checked representability before typed admission. Context masks retain all 64 unsigned bits. Negative or unrepresentable semantic values reject under the existing complete-map/event validation rules; changing display or adapters cannot reinterpret them.

| Record | Required fields and types | Defaults and constraints |
|---|---|---|
| `InputActionMapV1` | `SchemaVersion: Int32`, `MapId: Guid`, `Revision: Int64`, `InitialActiveContextMask: UInt64`, `Actions: ActionDefinition[]`, `Contexts: ContextDefinition[]`, `Bindings: BindingDefinition[]` | `SchemaVersion = 1`, first registered revision is 1, later revisions strictly increase, initial mask defaults to 0 and must name only declared contexts; it is used only on first registration. Arrays are non-`null`. `MapId` is unique in the router. GUIDs serialize in canonical lowercase `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` form. |
| `ActionDefinition` | `ActionId: Guid`, `Name: String`, `Kind: Digital \| Axis1 \| Axis2`, `DownPressThreshold: Float32?`, `DownReleaseThreshold: Float32?` | IDs and names are unique within the map (names compare ordinally). `Name` is valid Unicode with an integer UTF-8 byte count in `[1, 128]`; it is display/debug text, not identity. Digital actions have `null` thresholds. Axis actions default to 0.55/0.45, with `0 <= release < press <= 1`; Axis2 thresholds use vector magnitude. |
| `ContextDefinition` | `ContextId: Guid`, `Bit: UInt8`, `Priority: Int32`, `CaptureClasses: InputClassFlags` | `ContextId` and `Bit` are unique within the map; `Bit` is in `[0,63]`; `Priority = 0`, `CaptureClasses = None`. A context bit represents this context in a binding's `ContextMask`. |
| `BindingDefinition` | `BindingId: Guid`, `ActionId: Guid`, `ContextMask: UInt64`, `Priority: Int32`, `Kind: BindingKind`, `Enabled: Boolean`, `Flags: BindingFlags`, and the fields for that kind | IDs are unique within the map; action/context references must resolve. `Priority = 0`, `Enabled = true`, `Flags = None`; `ContextMask` is nonzero and may name only contexts in this map. The runtime representation is a typed native action-map schema encoded as `EBIN1` under [10](10-binary-data-and-authoring-formats.md). Masks encode unsigned 64-bit values, GUIDs canonical bytes, and enum kinds stable numeric schema IDs. JSON/XML are interchangeable authoring adapters; neither defines runtime ownership or layout. JSON authoring uses enum names, canonical GUID strings and fixed-width hexadecimal masks. Unknown fields/duplicate properties reject, never last-property-wins. IDs remain stable while editing and are not derived from names/indices. Stated defaults materialize before common semantic validation; other fields are required.

### Binding definitions

`BindingKind` is a versioned enum selecting a tagged native data schema, not a C# union/public exhaustiveness contract. Kind-specific fields are required exactly as listed after defaults are materialized; unknown kinds/fields and unknown flag bits are rejected. Named binding/source definitions have explicit properties and validators; a new kind requires schema/API compatibility review:

| Kind | Required source fields | Output and default processing |
|---|---|---|
| `Button` | `Control: DigitalControl` | Digital source for a keyboard HID physical key (`UsagePage: UInt16`, `Usage: UInt16`), named logical key, mouse button, or assigned-player gamepad button. |
| `Chord` | `Controls: DigitalControl[2..4]`, `CompletionWindowMilliseconds: Int32?` | Digital source. The sequence length is an integer in `[2, 4]`; `DigitalControl[2..4]` is schema cardinality shorthand, not a C# range or slice. Null means unbounded completion time; otherwise the integer millisecond value is in `[1, 60,000]`. Controls must be distinct. |
| `Axis1Keys` | `Negative: KeyboardControl`, `Positive: KeyboardControl` | `+1` for positive held alone, `-1` for negative held alone, and `0` when neither or both are held. |
| `Axis2Keys` | `Left`, `Right`, `Down`, `Up: KeyboardControl` | `X = (RightHeld?1:0) - (LeftHeld?1:0)` and `Y = (UpHeld?1:0) - (DownHeld?1:0)`; opposing keys cancel on their component, then vectors longer than 1 are normalized. |
| `GamepadAxis1` | `PlayerSlot: UInt16`, `Axis: LeftX \| LeftY \| RightX \| RightY`, `Invert: Boolean`, `Deadzone: Float32` | Assigned player only; input is clamped to `[-1,1]`. `Invert = false`; deadzone defaults to 0.15 and remaps `abs(x) <= d` to zero, otherwise `sign(x) * (abs(x) - d) / (1 - d)`; inversion follows deadzone. |
| `GamepadStick2` | `PlayerSlot: UInt16`, `Stick: Left \| Right`, `InvertY: Boolean`, `RadialDeadzone: Float32` | Assigned player only; normalized `[-1,1]` vector with length at most 1; `InvertY = false`; radial deadzone defaults to 0.15, then Y inversion; deadzone output is zero for `r <= d`, otherwise original direction times `min(1,(r-d)/(1-d))`. |
| `GamepadTrigger` | `PlayerSlot: UInt16`, `Trigger: Left \| Right`, `Deadzone: Float32` | Assigned player only; input is clamped to `[0,1]`, deadzone defaults to 0.05, output is `max(0,(x-d)/(1-d))`. |
| `AxisThreshold` | `Source: GamepadAxis1Source \| GamepadTriggerSource`, `Direction: Negative \| Positive \| Magnitude`, `PressThreshold: Float32`, `ReleaseThreshold: Float32` | Digital source evaluated after the source's deadzone/inversion processors. Defaults are 0.55/0.45; require `0 <= release < press <= 1`. `Magnitude` compares absolute axis magnitude; triggers accept only `Positive` or `Magnitude`. |

`GamepadAxis1Source` is `{Kind = GamepadAxis1, PlayerSlot, Axis, Invert, Deadzone}` with the same defaults as `GamepadAxis1`; `GamepadTriggerSource` is `{Kind = GamepadTrigger, PlayerSlot, Trigger, Deadzone}` with the same defaults as `GamepadTrigger`. An absent/disconnected assignment contributes neutral zero and cannot remain down. A normalized stick uses `+X = right`, `+Y = up`; adapters convert native Y conventions before bindings run. Clamp each stick component to `[-1,1]`, then normalize the vector if its length exceeds 1 before radial deadzone processing. Trigger values are 0 when released and 1 when fully pressed. `KeyboardControl` is `{Kind = KeyboardHid, UsagePage:UInt16, Usage:UInt16}` or `{Kind = LogicalKey, Name:String}`; `LogicalKey.Name` is valid Unicode with an integer UTF-8 byte count in `[1, 64]` and matches ordinally against the event's normalized logical-key name. `MouseButtonValue` is `Primary|Secondary|Middle|Auxiliary1|Auxiliary2|Auxiliary3|Auxiliary4|Auxiliary5`; `GamepadButtonValue` is `South|East|West|North|DpadUp|DpadDown|DpadLeft|DpadRight|Menu|Start|System|LeftBumper|RightBumper`. The `DigitalControl` authoring tagged object is `{Kind = KeyboardHid, UsagePage, Usage}`, `{Kind = LogicalKey, Name}`, `{Kind = MouseButton, Button:MouseButtonValue}`, or `{Kind = GamepadButton, PlayerSlot:UInt16, Button:GamepadButtonValue}`. Keyboard and pointer controls are `scoped` to the `InputRouter`'s focused-window route; each normalized control is held while any routed device generation reports it down, and releases only after all such sources report up or are removed. Each `PlayerSlot` has at most one assigned gamepad generation at a time; reassignment replaces it at a tick boundary, releasing the old generation before the new one contributes. An absent/unassigned gamepad never matches. Portable keyboard controls use the normalized HID usage pair; `LogicalKey` is an explicitly layout-dependent alternative. No binding stores native pointers, callbacks, or recycled device handles. Axis deadzones must be finite and satisfy `0 <= d < 1`. Axis-threshold sources use the same normalized source fields and processors as their analog counterparts. For an axis-threshold source, `Negative` compares `max(0,-x)`, `Positive` compares `max(0,x)`, and `Magnitude` compares `abs(x)` after source processors; press occurs at ` >= PressThreshold` and release at ` <= ReleaseThreshold`. Triggers are nonnegative. No custom processor code is accepted in a map.

`InputClassFlags` is the closed bit set `None = 0`, `Keyboard = 1`, `Pointer = 2`, `Gamepad = 4`; `BindingFlags` is `None = 0`, `ConsumePhysicalEvent = 1`. `CaptureClasses` and `Flags` may combine only declared bits; unknown bits are validation failures. `BindingKind` compatibility is fixed: `Digital` accepts `Button`, `Chord`, and `AxisThreshold`; `Axis1` accepts `Axis1Keys`, `GamepadAxis1`, and `GamepadTrigger`; `Axis2` accepts `Axis2Keys` and `GamepadStick2`. Digital actions require `null` thresholds; axis actions use both explicit threshold fields or neither (neither selects 0.55/0.45). Axis2 key controls must be four distinct keys; Axis1 negative/positive keys must differ. Deadzone and threshold values are finite binary32 values and are validated before publication.

The action-map registry is bounded: an `InputRouter` holds at most 16 maps; each map has at most 256 actions, 64 contexts, and 1,024 bindings; at most 256 contexts may be active in the router-wide ordered stack. Any capacity overflow rejects the whole registration/activation without changing the live map or stack. A map requires at least one context. Its active context mask is a `UInt64`; each context's unique `Bit` selects one bit, and every binding's nonzero `ContextMask` must be a subset of the map's declared context bits.

### Combination, ordering, and context semantics

Every action combines all of its currently enabled, eligible bindings with a fixed rule; maps cannot select a different combiner. A `Digital` action is the OR of its active binding states, and its `IsDownAtEnd` is exactly that aggregate: it presses only on aggregate false-to-true and releases only on aggregate true-to-false. Releasing one binding while another remains down emits no release. If the aggregate presses and releases on distinct ordered physical events in one tick, both transitions and both tick flags are retained even though `IsDownAtEnd = false`. `Chord` and `AxisThreshold` each contribute one digital binding state.

`Axis1` and `Axis2` actions select the single active binding output with greatest squared magnitude (`x * x` for Axis1, `x * x + y * y` for Axis2); this avoids last-writer/dictionary-order behavior. Exact magnitude ties select the lower numeric binding `Priority`, then the lexicographically smaller canonical `BindingId` GUID string. If no binding is enabled and eligible, the action value is neutral zero. Axis1/Axis2 output ranges are `[-1,1]` components, with Axis2 length at most 1. A trigger may contribute its `[0,1]` value to Axis1. Action `IsDown` uses hysteresis: when up, it becomes down at magnitude ` >= DownPressThreshold`; when down, it remains down until magnitude ` <= DownReleaseThreshold`. Each axis action emits `ValueChanged` when its effective value changes after processing (numeric component comparison with signed zero normalized to `+0`; NaN is invalid), and emits `Pressed`/`Released` on those `IsDown` transitions. For one input event, `ValueChanged` is ordered before that axis action's threshold edge.

Canonical physical event order remains `(HostTimestamp, HostSequence)`. For one event, update physical state and all affected binding states before recomputing each affected action once; this prevents a source handoff from manufacturing an aggregate release/press. Within a context, evaluate affected bindings in ascending `Priority` then `BindingId`; digital OR results do not depend on this order, and any matching `ConsumePhysicalEvent` leases the control for lower contexts. Action state/output identity is `(MapId, ActionId)`; emit results for different actions in ascending canonical GUID order by that pair. Binding ties use the stable `Priority`/`BindingId` order above; GUID comparison is ordinal over canonical strings, not .NET `Guid.ToByteArray()` order. Context ties use descending `Priority`, descending activation `InsertionSequence`, then ascending canonical GUID order by `(MapId, ContextId)`. The router-global `InsertionSequence` is positive `long`, starts at 1, and never wraps; replacing an active mask assigns increasing sequences to newly enabled bits in ascending `Bit` order. Map array/dictionary iteration order never affects results. A repeated OS key-down remains `Repeat`, never a second press. Per-tick action state contains the ordered transitions, `PressedThisTick`, `ReleasedThisTick`, `IsDownAtEnd`, and, for axis actions, latest value plus `ValueChangedThisTick`.

A chord is down only when every member is concurrently held. With no completion window, ordinary held modifiers remain valid indefinitely. With a configured window, the first member-down starts a deadline measured from its host observation timestamp; all members must be down when `TimeProvider.GetElapsedTime(firstTimestamp, memberTimestamp) <= TimeSpan.FromMilliseconds(window)` (the deadline is inclusive and does not assume a timestamp frequency). A repeat does not restart the deadline. Releasing any member before completion abandons the candidate; missing the deadline also abandons it. In either failure case, that chord binding is disarmed until every member is observed up, so a stale held modifier cannot complete a later chord. Once completed, it emits one press and remains down until the first member-up, then emits one release and remains disarmed until all members are up; remaining held members cannot retrigger it.

Contexts are ordered by descending `Priority`, then descending activation `InsertionSequence` (most recently activated first), then ascending canonical `ContextId`. A binding is eligible when its `ContextMask` intersects its map's active mask; if several named contexts are active, it is attributed to the highest-ranked matching context only. `ContextDefinition.CaptureClasses` is a flags mask over `Keyboard`, `Pointer`, and `Gamepad`. A higher-ranked active context capturing a physical class suppresses lower-context action evaluation for controls of that class; `BindingFlags.ConsumePhysicalEvent` similarly leases a matched physical control against lower contexts until that control is neutral/up. A `ConsumePhysicalEvent` chord leases all its member controls from the first member-down through completion or failure, and retains the lease until all members are up. Consumption never removes events from physical state tracking. When a lease begins, matching lower bindings are disarmed and contribute no action value; if the lower aggregate loses its active state, emit one `Canceled(InputConsumed)` rather than `Released`. Other still-down sources keep the lower aggregate active. Every disarmed binding continues receiving bookkeeping state but contributes no action value until its source is neutral: a button is up, all chord/key-axis members are up, a direct analog source's processed value is zero, or an `AxisThreshold` direction metric is at/below its release threshold. That neutral/up observation clears the disarm; only a later press/threshold crossing may contribute. All consumed releases and neutral samples clear disarmed controls, so no source can remain stuck.

Context activation/deactivation and active-mask replacement are atomic host-control commands applied at the next tick boundary, or at the host-control boundary when no world tick is admitted. `SetActiveContextMask` carries `MapId`, `ExpectedRevision`, and a complete `NewMask`; the host owner stamps it using the same `TimeProvider`/`HostSequence` ordering as physical events. Stale revisions, unknown bits, or router-wide context-capacity overflow return `Rejected` without mutation. Initial active bits and newly activated bits receive increasing insertion sequences in ascending bit order; insertion-sequence exhaustion rejects activation rather than wrapping. Context/map control staging is bounded to 256 outstanding commands; a full queue returns `CapacityExceeded` and never drops a mutation silently. Merge accepted context commands and physical events at that boundary by `(HostTimestamp, HostSequence)`; a mask replacement takes effect atomically at its position before any later sequence is evaluated. Recompute eligibility against the existing physical state without synthesizing presses. Any binding that becomes eligible while one of its sources is already non-neutral starts disarmed until that source's neutral/up condition, including bindings enabled by initial map registration or a mask change; held state never creates a new `Pressed`. If a context change masks a control already held by a lower-context action, disarm that binding until the source-specific neutral/up condition above, then recompute the aggregate from all remaining eligible, armed bindings using the mandatory combiner. Digital uses OR; an axis selects its new greatest-magnitude winner and preserves the existing action hysteresis state while evaluating that value. Losing one winner never forces zero while another eligible binding contributes. Emit `ValueChanged` if the effective axis value changes; emit one `Canceled(ContextMasked)`, not Released, only if the previously down aggregate becomes up. The cancellation sets `IsDownAtEnd` = false but retains the recomputed axis value, which need not be zero. For the same control change, `ValueChanged(newValue)` precedes cancellation; an aggregate that remains down has no cancellation/release/press edge. `InputConsumed` follows this same recomputation/order rule with its own reason. A later physical release/neutral sample is still processed for bookkeeping and does not emit a second action edge. Removing the masking context while the control is still non-neutral does not re-arm it; only the neutral/up condition followed by a new press/threshold crossing may activate that binding. Context-stack capacity/unknown-bit failures leave the previous mask and action states intact.

A map replacement validates the complete candidate and atomically publishes at a tick boundary. `MapId` must match the replaced map, `InitialActiveContextMask` must remain unchanged, and `Revision: Int64` must strictly increase without wrapping. Validation checks the schema version, all bounds, unique IDs/control tuples where required, resolved references/masks, compatible action/binding kinds, finite/ranged processors and thresholds, and closed enum/flag values. Any error returns `Rejected` with the first `ValidationIssue {Code, SchemaPath}` selected by ordinal schema path with RFC 6901 escaping/index rules, independently of authoring format; codes are `UnknownSchemaVersion`, `InvalidSchema`, `CapacityExceeded`, `MapIdentityMismatch`, `DuplicateId`, `DuplicateName`, `DuplicateControl`, `UnknownReference`, `InvalidContextMask`, `IncompatibleKind`, `InvalidEnumOrFlags`, `InvalidStringOrEncoding`, `InvalidProcessor`, `InvalidThreshold`, and `StaleRevision`. It preserves the complete prior revision; no partial map is visible. On success, active context membership is preserved by `ContextId` for contexts present in both revisions; removed contexts deactivate and new contexts start inactive. Existing active contexts retain their insertion sequences even if their bits change. Replaced active actions receive `Canceled(Rebound)` once, and controls already held are disarmed until their source-specific neutral/up condition before they can activate the new revision.

UI focus, pointer capture, and input consumption remain explicit requests supplied by the UI/game; the router does not implement hit testing or text layout. Capture requests are per-window and report granted/unsupported/denied. Wayland cannot grant global keyboard capture or global absolute pointer coordinates; its unaccelerated relative delta, when available, is a compositor-reported value rather than a guarantee of unprocessed hardware data.

## 5. Focus, pause, and held-control re-arming

Keyboard/pointer events route to the native focused window's recipients. Focus loss sends a sequenced host-control record to that window's `HostLiveUI` and attached `SimulationTimeline`; each cancels its own active window-sourced actions with `FocusLost` and clears/disarms their effective-down state. The simulation recipient also discards/counts its still-pending keyboard/pointer copies from the old focus route so they cannot activate after a later tick. Focus loss does not synthesize a release sequence or discard another recipient's/gamepad route; the UI recipient also ends/cancels active text composition. On focus regain, adapters publish a physical-state reconciliation snapshot where available (Windows foreground keyboard state/`GameInput` readings, Wayland `wl_keyboard.enter` pressed-key array, X11 keymap query); the snapshot is stamped at observation time and delivered as a new record to the target recipients. A platform aggregate keyboard snapshot does not claim per-keyboard identity; controls it cannot reconcile remain disarmed until their source-specific neutral/up condition in section 4. Controls known non-neutral become held-but-disarmed; known neutral controls are armed. If the adapter cannot reconcile a particular control, it remains disarmed until neutral/up is confirmed. Regain never synthesizes `Pressed` from a still-held key or axis and never seeds an earlier tick.

Pausing one simulation timeline leaves the host pump, `HostLiveUI`, and other timelines active but cancels only that recipient's gameplay actions with `Paused`, clears its gameplay-held state, and discards/counts only its pending copies. That timeline is not sent gameplay records while paused; its physical state is reconciled from a fresh timestamped snapshot on resume. Controls reported non-neutral remain disarmed until their source-specific neutral/up condition in section 4 and a later press/threshold crossing. `Input` is not accumulated for later gameplay and no pause duration is converted into buffered gameplay taps.

Device removal, window-focus loss, context masking, consumed input, mapping replacement, overflow, world pause, and recipient disposal are distinct action-cancellation reasons (`DeviceRemoved`, `FocusLost`, `ContextMasked`, `InputConsumed`, `Rebound`, `InputOverflow`, `Paused`, and `RecipientDisposed`). Consumers receive exactly one cancellation for each active action and cannot mistake cancellation for an ordinary physical release.

## 6. Text sessions and native IME contracts

The UI layer opens a `TextInputSession` on a focused window and supplies purpose/hints, an optional surrounding-text snapshot of at most 65,536 UTF-16 code units with selection offsets relative to that snapshot, a monotonically increasing document revision, and a caret rectangle in window-local logical units. The UI refreshes this snapshot after its own text edits; if native surrounding-text deletion extends outside the supplied range, the service emits `TextEditRejected` rather than editing unknown text. The input service forwards those hints and returns committed text, composition state, and ordered text-edit intents; it does not position glyphs, choose fonts, measure text, render underlines, or own layout. Session start/stop and focus changes are ordered; losing focus ends/cancels active composition.

The exact options/session declarations are in [30](30-public-api-review-surface.md#9-audio-and-input). TextInputSessionOptions requires the window, purpose, positive document revision, optional surrounding text, selection start/length and finite caret position/nonnegative finite size; hints default to None. Null surrounding text requires zero selection offsets. A present snapshot is valid Unicode, at most 65,536 UTF-16 code units, with checked in-range selection endpoints that do not split surrogate pairs. Unknown purpose/hint bits reject. Password or Sensitive sessions are always redacted; spelling/autocorrection hints cannot weaken that policy. Begin/Update/Dispose run on the host owner. Update preserves the window, purpose and frozen hints and requires a strictly greater revision; it atomically replaces the shadow snapshot/caret after complete validation. Disposed/inactive/foreign sessions cannot update. Dispose is idempotent, cancels composition and ends native session ownership without revoking previously copied batches. Native failures remain explicit capability/diagnostic outcomes, not an apparently active fallback session.

All strings are valid Unicode; API selection/cursor offsets use UTF-16 code units and may not split a surrogate pair. Native byte/code-point/ACP ranges are converted with checked boundary validation. Invalid native UTF-8 or an invalid selection range becomes a text-source diagnostic, not corrupted text. Text payload is bounded to 256 KiB total queued and 4,096 UTF-8-equivalent bytes per composition/commit record; overflow terminates the affected session with an explicit error and never silently truncates a committed string.

 * **Windows:** TSF is the primary IME boundary on the host STA owner. A focused session owns a TSF text-store/context and composition sink backed by a bounded engine-owned shadow text store initialized from the UI's text/selection snapshot. Synchronous TSF Component Object Model (COM) text-store reads and edits operate only on this mirror; each edit is copied into a bounded immutable batch tagged with session and base/result document revisions. The mirror exists only to satisfy TSF's synchronous native protocol and is not a second authoritative or saved document. COM methods/sinks do not call UI/document code, invoke arbitrary system/user callbacks, wait, or run asynchronous continuations. They only validate/update the mirror and copy protocol records, returning promptly; text-store capacity/validation failure returns a native error without partial mutation. After the native/COM callback stack has returned, the host owner dispatches the copied batch to UI code. UI applies an edit only if its document revision matches the intent's base revision; otherwise the service reports `StaleMirror`, discards dependent intents, and requests a fresh authoritative UI snapshot before more edits are accepted. The UI also supplies caret geometry through the session. Committed text is emitted once from the accepted text-store insertion/commit operation; preedit updates and composition end/cancel are separate records. Physical keys come from Raw Input, not text-message reinterpretation. If TSF/context initialization fails, expose `TextCompositionUnavailable`/`TextCommitUnavailable` with native HRESULT; do not claim IMM/IME composition from physical keycodes. A separately implemented legacy IMM32 adapter may be selected explicitly, with its own capability status and no concurrent duplicate TSF delivery.
 * **Wayland:** Bind `zwp_text_input_v3` only if the compositor advertises it and a text session is active. Send enabled/content type, surrounding text/selection, and caret rectangle when the UI supplies them. Treat `preedit_string`, `commit_string`, delete-surrounding requests, and `done(serial)` as one protocol-batched update; publish only after the matching `done`. Expose delete-surrounding as an ordered text-edit intent for the UI to apply before the associated commit; the input service never mutates the UI text model. Do not treat this optional/unstable protocol as present on every compositor. If unavailable, xkbcommon compose/dead-key output may provide simple committed text, but IME composition and surrounding-text editing report unavailable.
 * **X11:** Create XIM/XIC for the focused text session and use the Xlib input-method lookup/preedit callbacks for committed and composing text. If no usable XIM exists, use xkbcommon compose for simple committed text and report composition unavailable. Never derive text from action names or physical key labels.

Composition records have stable sequence and semantics: `CompositionStarted`; zero or more `CompositionUpdated` records replacing (not appending to) the prior preedit string and selection; either one `TextCommitted` containing the committed UTF-16 string followed by composition end, or `CompositionCanceled` with reason. Empty commits are not emitted. A native IME may commit multiple Unicode scalars in one record. UI decides how to render composition/selection and applies requested delete/replace ranges to its own text model.

### Recording and replay

Each `InputRouter` has an independent optional `InputRecorder`. A replay stream records its `InputRecipientKind`, physical event copies with original process-wide `HostSequence`, event-time `UiInputDisposition`/route changes, its own assigned ticks and [03](03-shared-conventions-and-clocks.md) segment revisions (none for `HostLiveUI`), focus/context/map-revision/device-generation changes, cancellation/reconciliation, action-map version, and any routed text. The same captured `HostSequence` may therefore have different `AssignedTick` values in different timeline streams. Host-control overflow/reconciliation, pause, focus reset, and disposal are recorded for only their recipient with dropped sequence ranges even when no world tick is admitted; they are not assigned fabricated future ticks. Replay feeds one recipient's copied events before that recipient's same tick stage and reproduces its host-control boundaries separately; it never reads live native state, drains a sibling stream, or re-evaluates UI capture from a later UI state. It does not pretend different OS keymaps/native timestamps are byte-identical. Recorder is off by default. Committed text recording is separately opt-in per `HostLiveUI` text session. Password/sensitive sessions never persist text payload; they record `SensitiveTextRedacted` and mark any replay that depends on that payload as incomplete rather than claiming strict fidelity. Queue overflow, unknown mapping or unreconciled source state marks only that recipient's recording discontinuous and non-certifying. Recorded intentional pause/discard and terminal disposal are replayed as defined control operations, not mislabeled as unknown input loss.
