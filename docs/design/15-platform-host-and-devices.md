# Platform host and devices

[Terminology and reading conventions](01-terminology-and-reading-guide.md).

This chapter specifies native host, window, adapter-selection, and device-lifecycle behavior. [00](00-overview-and-scope.md) owns product scope.

## 1. Supported profile and native boundary

| Host profile | Required implementation |
|---|---|
| Windows 11 x64 interactive | Win32 windows/message queue, per-monitor-v2 DPI, D3D12 through DXGI, Vulkan through Win32 WSI, event-driven shared WASAPI |
| Ubuntu 24.04 LTS x64 interactive | Wayland by default, explicit X11 selection/fallback, Vulkan through the selected WSI, `PipeWire` playback |
| `Headless` | No display connection, window, GPU, audio endpoint, or physical input device is opened |
| `OffscreenNative` | Real selected D3D12/Vulkan GPU creates offscreen images; no windows/display/WSI/swapchain; audio and physical input are not requested unless explicitly configured |

The engine owns policy and its host/device state machines. Native calls are confined to backend assemblies using reviewed application binary interface (ABI) declarations (`LibraryImport`, function pointers, and Component Object Model (COM) interfaces where appropriate); native pointers do not escape those assemblies. No SDL, GLFW, MonoGame, or other engine/windowing framework substitutes for the specified adapters. Reusable operating system (OS) libraries and protocol bindings are allowed.

`TerraFX.Hosting`'s `EngineHost` is in `TerraFX.Runtime`; native window/input adapters remain in `TerraFX.Platform`, which depends only on Core/Input. Host-to-platform composition does not add a reverse platform-to-Runtime edge or make a headless host open native services.

Windows uses `user32`/Win32 for windows and message pumping, DirectX Graphics Infrastructure (DXGI) + D3D12 for D3D12 presentation, Win32 Vulkan window-system integration (WSI) for Vulkan, and `Core` `Audio` COM application programming interfaces (APIs) for Windows Audio Session API (WASAPI). The engine sets Per-Monitor-V2 awareness before the first window is created and verifies the effective process/thread context; a late awareness change or Windows dots per inch (DPI) virtualization is not accepted as a valid interactive host.

Linux uses `libwayland-client` and generated client bindings from the installed Wayland protocol XML for Wayland, `libxkbcommon` for keymap state and compose handling, and Xlib/XInput2/`XRandR` with `libxkbcommon-x11` for the explicitly selected X11 adapter. Linux device discovery/seat permissions are delegated to the OS (`udev`/logind); the engine does not require root, rewrite system permissions, or pretend that a sandboxed process can open an inaccessible node such as `/dev/input/event*`.

The native host targets one process and one host-owner thread. Multiple windows (default maximum 32) share that host/pump; each has independent focus, monitor/scale metrics, surface/swapchain lifetime, and close state. A host does not create one native message loop per window. Version 0.1 admits at most one interactive/physical-input capture host per process; a second receives `NativeHostAlreadyActive` before native registration. This protects process-wide Raw `Input`/DPI registration and single-capture routing. Independent `Headless` or `OffscreenNative` hosts without physical input may coexist, with separate `Core` owner IDs; multiple audio mixers are independently owned and do not claim a shared input route.

## 2. Adapter selection and capability reporting

Backend choice is explicit and is reported after startup as both requested and selected backend:

| Option | Behavior |
|---|---|
| `WindowsNative` | Use Win32 on Windows; unsupported on other OSes |
| `WaylandOnly` | Linux default. Connect to the session compositor; failure is a startup/capability result, not a reason to switch to X11 |
| `WaylandThenX11` | Explicit opt-in fallback. Try Wayland first, then X11; report both the Wayland failure and the selected X11 backend |
| `X11Only` | Explicit X11 configuration; fail if no usable X server |
| `Headless` | Do not probe or load a window-system/GPU/audio/input backend |
| `OffscreenNative` | Require an explicitly selected D3D12 or Vulkan backend and a successfully created device on the selected real GPU adapter from [17](17-graphics-device-and-resources.md); the Null renderer is not eligible. `Create` offscreen images without windows, display connections, presentation surfaces, or swapchains. `Audio`/physical-input services are `NotRequested` unless independently configured. Vulkan uses the core device profile in [17](17-graphics-device-and-resources.md) but does not enable/require WSI extensions, `VK_KHR_swapchain`, or `VK_EXT_swapchain_maintenance1`/its promoted alias. |

There is no automatic D3D12-to-Vulkan, Vulkan-to-D3D12, Wayland-to -X11, `PipeWire`-to-`PulseAudio`/ALSA, or physical-to-`null`-device fallback. A caller may explicitly choose a different backend and restart. Startup results and later capability changes use a typed state (`Available`, `Unavailable`, `Unsupported`, `PermissionDenied`, `DeviceLost`, or `NotRequested`) with a stable diagnostic code, operation, native result where applicable, and epoch. A boolean `IsSupported` alone is insufficient.

Each feature declares whether it is `Required` or `Optional`. A required feature that cannot start fails host creation with its diagnostic. An optional feature leaves the host usable and reports `Unavailable`; it never returns a working-looking `null` device. In `Headless`, display, graphics processing unit (GPU), physical audio, and physical input are `NotRequested`. `OffscreenNative` requires a real GPU and never creates a window/display/WSI surface; use an interactive profile for visible presentation or clipboard. `Audio`/input remain `NotRequested` unless individually configured and then report actual availability. Synthetic test adapters require a separately named explicit test option and are never represented as physical devices.

Capability discovery is per actual display/compositor/device. In particular:

 * Wayland capabilities are protocol globals actually advertised by the compositor. `xdg-shell` is required for interactive top-level windows. Fractional scale, text-input-v3, relative-pointer, pointer-constraints, data-device/clipboard, and decoration negotiation are optional. Absence is reported individually; no compositor is assumed to implement all protocols or honor every request.
 * Wayland does not expose global pointer coordinates or general global keyboard capture to ordinary clients. The API returns `Unsupported` for such requests. Relative-pointer and pointer-lock behavior is available only when the corresponding protocols are advertised and the compositor grants the request; accelerated and compositor-reported unaccelerated relative deltas remain distinct values.
 * X11 support is the selected X server's actual protocol/extensions, not a promise that every modern Wayland feature has an X11 equivalent.
 * D3D12 is Windows-only. Vulkan is implemented on Windows and Ubuntu, but interactive Vulkan requires the selected WSI extension, swapchain support, and the graphics requirements in [00](00-overview-and-scope.md)/[17](17-graphics-device-and-resources.md). An unmet requirement is a diagnostic refusal, not a backend substitution.

### Native clipboard text service

`ClipboardText` is a platform-host service, not an `InputRouter` feature. It has independent `Required`/`Optional` admission. Explicitly required but unavailable service fails host creation; optional admission keeps the host usable and exposes the typed capability result. The editor requests the optional service; gameplay input does not require it. A caller may require it for a workflow that cannot operate without clipboard access.

`ClipboardTextService.ReadTextAsync(ClipboardReadRequest, CancellationToken)` and `WriteTextAsync(ClipboardWriteRequest, CancellationToken)` marshal native access to the host owner and complete with the typed result above; each request carries its target `WindowHandle`, maximum UTF-8-equivalent byte count (at most 1 MiB), and optional one-use `UserGestureToken`. Wayland paste/copy requires a valid token. Callers never hold an OS clipboard/data-offer/selection pointer. Wayland/X11 transfers stay asynchronous while the host continues pumping; Windows copies the bounded payload while the clipboard is open. `Completion` continuations are asynchronous and never run in a native clipboard callback. Clipboard requests are not accepted in `Headless` or `OffscreenNative`; a request is `Unsupported`, and required admission fails host startup. If it is not requested in those profiles, its state is `NotRequested`.

 * Windows uses the Win32 Unicode clipboard (`CF_UNICODETEXT`) on the host-owner thread. Open/read/write failures are returned with their native status; text is copied into engine-owned memory before clipboard storage is released.
 * Wayland uses the focused seat's `wl_data_device` and advertised text MIME types. A paste or copy request carries a one-use user-gesture token bound to the originating focused surface/input serial. Copy creates an owned `wl_data_source` whose immutable bytes remain alive until selection loss/cancellation; a transfer runs through the owner pump without blocking it. Missing, expired, or compositor-refused authorization returns `PermissionDenied`/`SelectionExpired`; the service does not query a global clipboard around compositor policy.
 * X11 requests the `CLIPBOARD` selection as `UTF8_STRING` or `text/plain;charset=utf-8`, handles the asynchronous selection transfer, and invalidates the request if its owner/selection changes before a complete copy. Copy retains its immutable selection payload and serves protocol requests until ownership is lost.

`ClipboardReadResponse`/`ClipboardWriteResponse` are dedicated immutable domain responses with a `ClipboardStatus` enum: Completed, `NoSelection`, `Unsupported`, `PermissionDenied`, `SelectionExpired`, `TimedOut`, `InvalidData`, `TooLarge` and applicable protocol `Canceled`. Read Text is present only for Completed; Completed with Text = "" means genuinely empty clipboard text, not fallback for denial/loss/failure. Expected selection/permission/payload outcomes carry native diagnostic context; misuse/unexpected adapter/invariant errors fault the `Task` instead of returning a generic `Failed` response. `CancellationToken` cancellation follows the `Task`/lease contract separately from a protocol-terminal `Canceled` response. The service copies and validates complete UTF-8/UTF-16 payload before releasing native storage, caps text at 1 MiB UTF-8-equivalent, and never returns partial selection as success. A refused paste is surfaced so user interface (UI) can disable/report Paste.

## 3. Host ownership, pump, and window API contract

`EngineHost` creates one long-lived host-owner thread before native initialization. On Windows it initializes COM as STA on that thread before creating windows or TSF state; it uninitializes COM only after those objects are released. Window creation/destruction, native event dispatch, UI-facing callbacks, window-state transitions, and `PlatformHost` commands run on this owner. The frame/tick admission order is the shared pipeline: native pump/UI and host-control services; input consumption and `Early` gameplay; animation/kinematic updates; physics/transforms; sorted physics events/`Late`; final structural commit; immutable render/audio extraction; `Stage9` publication. Worker jobs may calculate data but cannot call the native window API.

`Task` completion is not a thread-affinity guarantee. Calls from another thread use a bounded host command mailbox (capacity 512 outstanding by default) and complete only after owner application. A full mailbox accepts/applies nothing: `TryInvoke` returns false, named window-command responses can report `QueueFull`, and non-Try `InvokeAsync`/`CreateWindowAsync` fault their `Task` with contextual `InvalidOperationException` rather than pretending application succeeded. `Completion` sources use asynchronous continuations; user continuations never run inside native callbacks or host locks. The owner never synchronously waits for its own pump. Native `WndProc`/protocol callbacks only copy events, never invoke application code, wait for tasks or block for simulation; managed dispatch follows native return.

The host continues to pump native messages while rendering is minimized, simulation is paused, or the application is shutting down. Simulation catch-up limits in [03](03-shared-conventions-and-clocks.md) do not starve window/configure/device events. The pump waits on native readiness plus the host scheduler's waitables; it does not busy-spin. Each delivered native event is assigned a monotonically increasing host sequence and a timestamp from the private monotonic source when observed, initially backed by `TimeProvider`. Public clock domains/conversion follow [03 section 2](03-shared-conventions-and-clocks.md#2-four-clocks), not the backing object's API. Monotonic sequence overflow is a host fault, never wraparound.

Public calls follow this shape:

 * Static `EngineHost.StartAsync(EngineHostOptions, CancellationToken) -> Task<EngineHost>` creates the dedicated owner thread, initializes adapters there, and completes only when the host is running or startup has failed. Calling or awaiting it does not transfer native ownership to the caller.
 * Instance `InvokeAsync(Action<EngineContext>, CancellationToken)` returns `Task` for a bounded synchronous owner callback. The callback returns promptly, cannot await/retain context or wait for its own completion. Success completes only after return; callback/unexpected dispatch failures fault that `Task` with the original exception, cancellation follows [02](02-dotnet-api-memory-and-ownership.md), and queue-full behavior is above. Invoke is not a transaction: callback failure does not undo earlier completed owner operations or automatically retry the callback; tick faults still follow [13](13-jobs-and-frame-pipeline.md). No `Task<Completion>`/Result wrapper or caller-thread Run/`RunAsync` pump is introduced.
 * `TryInvoke(Action<EngineContext>, CancellationToken, out Task? completion)` is a synchronous admission alternative with `NotNullWhen(true)` on completion: true accepts once and supplies the same asynchronously completed/faulted `Task`; false means only `QueueFull`, leaves completion `null` and has no acceptance/side effect. Invalid arguments/disposed host throw, and a pre-canceled token throws `OperationCanceledException` before admission. `InvokeAsync` represents token cancellation with its canceled `Task` instead. This keeps false single-mode and does not hide callback failure as capacity failure.
 * `EngineHost.CreateWindowAsync(WindowOptions, CancellationToken)` returns a `WindowCreationReceipt`; its `Created` outcome carries the stable engine `WindowHandle`, not an HWND/XID/`wl_surface * `.
 * Owner-thread `EngineHost.GetSurface(WindowHandle)` returns the existing host-owned logical `Surface` for an interactive window. Successful interactive creation establishes the mapping before its receipt completes. Default/foreign handles throw `ArgumentException`; stale/closed handles, off-owner access, or a window without a graphics surface throw `InvalidOperationException`. Closing invalidates the logical mapping immediately; native storage still waits for actual graphics and presentation retirement. This bridge belongs to `Hosting`, not a `Graphics` dependency on `Platform`.
 * Window mutators return dedicated `WindowCommandReceipt` values, synchronously or through `Task` after owner application, with their operation/status/owner sequence/native diagnostic. Invalid/disposed/foreign input at admission throws; a valid admitted window that closes before application can receive Disposed rejection. Expected compositor unsupported/denied/unconfirmed and queue-capacity outcomes remain domain receipts; unexpected native/invariant failure faults the `Task`. Later compositor state-change events distinguish acceptance from actual compliance.
 * `EngineHost.StopAsync` is idempotent and requests ordered shutdown on the owner. Its completion follows owner-thread native disposal and thread termination. Canceling its wait does not undo accepted shutdown. The host rejects new window/device commands after the stop boundary.

`EngineHost.Renderer` is the initialized logical extraction service in every profile. In `Headless`, it validates/copies committed scene data without a native device; `GraphicsDevice` and `GpuResidency` remain absent, and native graph construction/submission refuses explicitly. `OffscreenNative` uses real same-device texture targets and readback through [17](17-graphics-device-and-resources.md)/[19](19-render-graph-synchronization-and-presentation.md), not fabricated windows or presentation surfaces.

The host exposes native errors and lifecycle events as immutable records with `WindowHandle`, `SurfaceEpoch`, `SwapchainEpoch`, source timestamp/sequence, stable code, and native status. Managed subscribers run on the host owner only after native callbacks have returned. Invoke subscribers individually in captured registration order using chapter [13](13-jobs-and-frame-pipeline.md)'s isolated delivery policy: report `SubscriberDeliveryFailed` with the original exception, continue other subscribers and never retry or reverse the already observed native lifecycle. Exceptions do not escape an `unmanaged` callback.

## 4. Window options, metrics, and native behavior

`WindowOptions` is validated before any native mutation:

| Field | Default and contract |
|---|---|
| `Title` | Non-`null` UTF-16 string, no embedded NUL; title is presentation text, never a persistent identity |
| `ClientSize` | 1280 x 720 logical content units; each dimension is positive and checked when converted to native pixels |
| `MinimumClientSize` | 1 x 1 logical unit |
| `Resizable` | `true` |
| `Visible` | `true`; headless creation is rejected rather than returning a fake window |
| `Mode` | `Windowed` |
| `Monitor` | `null` means OS/compositor default placement; a requested monitor that disappears is an explicit placement failure/notification |

The public `WindowMetrics` separates `ClientPixelSize`, `LogicalClientSize`, `ContentScale`, effective DPI, DPI source/confidence, `SurfaceEpoch`, and `SwapchainEpoch`. Pixel dimensions describe the drawable buffer and are authoritative for swapchain extent. `SurfaceEpoch` identifies the current lifetime of the backend's actual native presentation target (`VkSurfaceKHR` for Vulkan WSI, or the window target bound to an implicit-surface API such as DXGI); it changes only when that native target is successfully replaced. `SwapchainEpoch` identifies a successfully created back-buffer/image generation and changes on each successful swapchain creation/recreation, including resize. Each begins at 1 on its first successful creation; 0 means never created. Retired/lost resources are explicitly unavailable even while their last epoch remains in the metrics; generations never wrap. Logical units are 1/96 inch where the platform supplies meaningful scale. Rounding from logical to pixels is nearest integer, ties to even, with checked range validation. A platform that cannot report trustworthy DPI reports `Unknown`/`Assumed96Dpi`; 96 DPI is not represented as measured hardware fact.

 * **Windows DPI:** Manifest/process configuration is Per-Monitor-V2 before window creation. On `WM_DPICHANGED`, consume the OS-suggested outer rectangle, publish the new effective DPI and client pixel extent, and resize the swapchain only after the graphics owner has retired prior uses. `WM_DPICHANGED_AFTERPARENT` is forwarded for child windows if the host later provides them. Moving across monitors does not silently scale the application's logical coordinate contract.
 * **Wayland:** Apply `xdg_surface.configure` serials with `ack_configure` in protocol order and use the compositor's configured size/state; the requested size is not authoritative. Use `wp_fractional_scale_v1` plus viewporting only when both protocol objects are advertised. Otherwise use the compositor/output's integer `wl_surface` buffer scale. `Scale` changes invalidate the drawable extent and retire/recreate the swapchain generation (`SwapchainEpoch`); they do not replace the native surface or increment `SurfaceEpoch`.
 * **X11:** Report pixel extents from the X server. Obtain scale from an explicit application override or a recognized X settings source; otherwise report `Assumed96Dpi`, not a fabricated monitor DPI. `XRandR` monitor changes are asynchronous and may invalidate placement/extent.

Window metrics may coalesce resize/move bursts to the latest extent before render extraction; focus, close, keyboard, pointer-button, text, device-removal, and failure events are ordered records and are not silently coalesced. `Rendering` waits for a nonzero drawable size; a zero/minimized extent suspends presentation without manufacturing a 1 x 1 swapchain.

### Monitor enumeration

Owner-thread `PlatformHost.GetMonitorHandles()` returns a copied immutable array in stable discovery order. Each monitor has a host-issued `OwnerId`/`Index`/`Generation`, default invalid; hotplug removal invalidates its generation and emits a sequenced lifecycle observation. Discovery ordinals never wrap/reuse. Returned handles do not retain native monitor storage or guarantee that a later request can place a window there.

`WindowOptions.Monitor` is nullable for compositor/default placement. A stale/foreign handle rejects window-creation admission; a monitor removed after valid acceptance produces a `WindowCreationReceipt` with `Rejected` status and `MonitorUnavailable`, without silently selecting another requested monitor. Native placement/compositor compliance remains separately observed. Headless/offscreen display admission remains `NotRequested`; an empty enumeration is not evidence that a physical display backend started.

### Fullscreen and monitor policy

`WindowMode` is `Windowed`, `BorderlessFullscreen`, or `ExclusiveFullscreen`. Borderless is the portable fullscreen mode. `ExclusiveFullscreen` is a separately requested Windows/DXGI mode only; D3D12 may request DXGI exclusive state, and Vulkan may use it only if the relevant optional Win32 extension is present. It is not a Linux capability and is not inferred from a full-screen compositor state.

On Wayland, fullscreen is an `xdg_toplevel.set_fullscreen` request; the compositor selects/announces the actual state and output. The engine never changes display mode or claims exclusive ownership. X11 sends an EWMH fullscreen request and reports the state observed from the window manager; it does not change the monitor mode by default. `Unsupported` mode requests return `Unsupported`. Denied, unconfirmed, or failed transitions preserve both requested and observed state, emit a diagnostic, and do not claim success. A transition awaiting external confirmation times out after five host seconds with `Unconfirmed`; a later compositor response still updates actual state.

Monitor IDs are host-local generation-checked handles. Refresh rate, physical size, scale, and connection state are nullable/qualified measurements; no fixed refresh, scale, or display-mode-switch capability is assumed. Monitor removal during fullscreen produces an explicit transition and uses the platform's safe windowed/borderless recovery behavior without treating the requested mode as active.

## 5. Graphics surfaces, epochs, and loss

The platform backend creates native surfaces only for the selected explicit graphics backend. Win32 windows can back D3D12/DXGI or Vulkan Win32 surfaces. Wayland windows can back Vulkan Wayland surfaces; X11 windows can back Vulkan Xlib surfaces. D3D12 on Linux is unsupported. `Headless` creates no graphics surface or device. `OffscreenNative` creates a real graphics device and offscreen images but no window, WSI surface, or swapchain.

`SurfaceEpoch` and `SwapchainEpoch` are independent monotonically increasing `uint` generations per window. `SurfaceEpoch` identifies a live native presentation-target lifetime; `SwapchainEpoch` identifies its live back-buffer/image set. A resize/recreation retires the prior swapchain generation and increments only `SwapchainEpoch` after its replacement succeeds; it does not increment `SurfaceEpoch`. Replacing the underlying native presentation target revokes its prior epoch and assigns the next `SurfaceEpoch` only after successful creation; any replacement swapchain receives its own next `SwapchainEpoch`. A stale presentation handle is rejected before native use. Back-buffer/image handles additionally carry `DeviceEpoch`; every asynchronous pick/readback request/result carries `DeviceEpoch`, `SurfaceEpoch`, and `SwapchainEpoch` and is accepted only if all three still match live resources; an old-epoch result returns an explicit stale-device/surface/swapchain result rather than selecting a recycled image/entity. A retired generation is never made live again.

Graphics-device loss is separate from surface and swapchain loss. `DeviceEpoch` is 1 for the first successfully created graphics device. On D3D12 removal/reset/hung or Vulkan `VK_ERROR_DEVICE_LOST`, immediately revoke admissions against the old epoch, stop submissions, and publish `GraphicsDeviceLost`; no old handle can be used while recovery is attempted. The numeric epoch advances only when a replacement device has been successfully created, validated against the required profile, and published. `Failed` replacement attempts leave the old epoch revoked and no active device; they do not increment it or restore old handles. Successful replacement gets the next epoch, and every handle/resource tied to the old device remains stale even if indices are reused. If the driver/resource lifetime is uncertain, retain/quarantine native ownership until teardown proves safe reclamation.

 * D3D12 removal/reset/hung and Vulkan `VK_ERROR_DEVICE_LOST` produce `GraphicsDeviceLost` with operation, adapter, native code, and revoked old epoch. `Stop` submissions and reject old-epoch handles before attempting recovery; reconstruct only resources whose central processing unit (CPU)/asset ownership permits it. No driver call is assumed recoverable.
 * A platform resize/configure suspends acquisition on the affected surface until the new nonzero metrics are applied. Other windows and the host continue.
 * A WSI/surface loss is `scoped` to that surface unless the native API reports whole-device loss. Per-window swapchain failure does not masquerade as successful presentation.
 * Adapter selection, format/feature requirements, and refusal to start are observable through a capability snapshot. No fallback uses an unrequested API or downgraded renderer.

## 6. Headless, native events, and shutdown

`Headless` supplies simulation/assets/jobs without windows/display/GPU/audio endpoint/physical input. `OffscreenNative` requires its real selected GPU/images, not windows/display/WSI; audio/input remain `NotRequested` unless independently configured/admitted. Capability queries return actual `NotRequested`/`Unsupported` states. In either no-window profile, `CreateWindowAsync` faults its `Task` with `NotSupportedException` and stable `Unsupported` diagnostic, with no handle/native side effect; it does not return a status in place of a `WindowHandle` or silently change profiles. Explicit Synthetic input/Offline audio test adapters cannot satisfy a physical device/visible-presentation requirement.

Window lifetime is `Creating -> Open -> CloseRequested -> Closing -> Closed`; failure before Open faults `CreateWindowAsync`'s `Task` after cleanup and returns no live handle. A native close button emits `CloseRequested`; application policy may accept/defer it. Only owner shutdown destroys the native window. Once closing is accepted, new surface commands are rejected and graphics releases wait for last-use fences.

Shutdown order is: stop new host commands; finish/cancel accepted frame work according to the owning subsystem; stop audio/input producers and cancel/complete accepted clipboard transfers; keep pumping until native close/configure callbacks and owner-thread releases have completed; retire window swapchains/surfaces after their fences; destroy native windows; release clipboard/data-device objects and display connections/COM apartment; terminate the owner thread. Default native shutdown wait budget is five seconds as in [02](02-dotnet-api-memory-and-ownership.md). Timeout reports the still-live operation and retains any native resource that may still be in use; it does not free memory beneath a driver or claim successful disposal. A host-owner thread never synchronously joins itself.

| PF07 | Move a Windows window between 100% and 150% monitors; separately resize a Wayland window and deliver configure serials; resolve a delayed pick after resize and after native-surface replacement. | Metrics report both epochs and actual pixel/logical sizes/scale provenance. | PF09 | Fill the 512-entry host mailbox and submit one more title/resize, `TryInvoke` and non-Try `InvokeAsync` operation. | First 512 are accepted in queue order; overflow has no native side effect: window command gives `QueueFull` receipt, `TryInvoke` false/`null` and `InvokeAsync` faulted `Task`. | PF11 | `Start` with optional and required `ClipboardText` under a compositor without data-device; while paused/minimized deliver close/focus/text/resize; then copy/paste under a valid Win32/X11 selection and a refused/expired Wayland gesture or changed selection owner. | Optional host starts with unavailable capability; required startup fails.
