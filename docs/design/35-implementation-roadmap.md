# Implementation roadmap and acceptance milestones

[Terminology and reading conventions](01-terminology-and-reading-guide.md).

This chapter owns implementation prerequisites, coherent work units, and acceptance boundaries. Subsystem chapters own behavior; the roadmap refers to those contracts rather than restating them. [00](00-overview-and-scope.md) defines the clean-slate product scope.

Current milestone status, implementation progress, blockers and execution evidence belong in [the project roadmap](../project/Roadmap.md), not in these milestone definitions.

## 2. Implementation prerequisites and handoff

Coherent milestone work lives in its assigned namespace folders in Runtime where applicable; milestones are not instructions to recreate the former per-subsystem assemblies. Incremental implementation does not justify splitting the specified package graph. [29](29-project-setup-build-and-deployment.md) owns repository policy; this chapter assigns when its checks and the subsystem observations become applicable.

### 2.1 M01 readiness

M01 verifies the supplied foundation and prepares implementation. Satisfactory existing infrastructure is retained rather than rebuilt. Its exit evidence is:

| Readiness input | Required evidence |
|---|---|
| Repository mapping | Verify the actual solution, shared/folder props and targets, `.editorconfig`, centrally selected packages, scripts, CI, test conventions and artifact paths against [29](29-project-setup-build-and-deployment.md). Preserve signing/publication and the ordinary `dotnet` entrypoints; do not require a replacement build or test orchestrator. |
| Assembly and package policy | Verify the thirteen production projects under sources, repository-only tools under tools, BCL-only Core, minimal direct references and one Runtime assembly for seven semantic namespaces. Engine release versions align while project references use normal SDK-generated NuGet dependency ranges. No custom exact-version pack hook, default lockfile or new physical subsystem boundary is required. |
| Development and test foundation | Verify the compatible developer SDK selection and centrally selected NUnit/VSTest setup through ordinary restore/build/test, Debug before Release. Retain the existing result logging. Record known empty scaffold suites as having no engine tests; do not add placeholder cases or claim engine qualification from their successful test command. |
| Contract triage | Map known supporting-declaration, descriptor, registration and capability gaps to their owner contracts and affected units. Distinguish genuinely unresolved contracts from declarations already specified but not implemented. Do not require the entire future engine catalogue, all built-in schemas or complete application callers to exist before Core work begins. |
| First implementation unit | Identify a concrete dependency-ready M02 unit and its exact prerequisite revision, accepted signatures/supporting declarations, defaults, ownership/error/completion rules, allowed dependencies, acceptance observations and validation profile. Resolve any contract gap needed by that unit before it begins; a gap in an unrelated future feature is not its prerequisite. |
| Readiness evidence | Record the baseline revision, actual commands/exits, SDK/runner identities, discovery/execution counts and artifact locations, including absent tests and unavailable capabilities. This is repository-readiness evidence, not a supported shipping profile, native witness, published-AOT result or completed AR/BN/EN case. |

M01 is complete when these readiness inputs are established and the first M02 unit can start under accepted contracts. It does not require production implementations, speculative generated registries, a custom qualification framework, package-consumer matrices, native execution or release manifests. A successful scaffold build/pack is not evidence that those later requirements have passed.

### 2.3 Unit prerequisites and handoff

For each unit, inventory every reachable supporting type against its owning declaration or exact generation descriptor, including namespace, representation, constructor/issuer, default state, fields/nullability, borrowing and disposal authority. An unresolved entry blocks the affected unit, not unrelated work; record the precise missing decision rather than inventing a stub. Absence from a facade-only projection is not proof that the owner contract is missing. No unresolved public signature, schema assignment or lifecycle rule reaches implementation.

AR01/AR02/NM05 exercise typed/default/named overloads, narrow operator interfaces, char/UTF-8 formatting metadata and nullable codec flow with their owning surfaces; negative borrowed-span retention must fail compilation. M02 implements/qualifies the formatter text/culture/destination/allocation behavior, named SinCos pair and exact Angle definitions. M03 covers tag registration/atomic edits and scene option budgets; M04/M08 cover text/session and UI snapshot lifetimes; M07 covers six Audio Async names, bus outputs and cached snapshot publication. Shared async usage/admission/execution/cancellation/continuation and ValueTask protocol rules apply at every owning milestone. [37](37-completeness-and-audit.md) distinguishes existing specification/compiler evidence from implementation qualification.

Each implementation assignment names one coherent subsystem/feature, exact prerequisite revisions including the accepted descriptor-manifest and golden-fixture revisions whenever it implements a reader/writer, schema tags, public signatures, ownership/lifetime/ordering/error contracts, allowed dependencies, exclusions, acceptance IDs, test profile and build-output owner. A golden-fixture revision includes its independent source/materializer, literal inputs and mutation rules, static standalone output lengths/hashes, compact-range base/boundary/aggregate hashes, semantic/status facts, oracle revisions and approvals; tests may materialize those expected bytes in memory but may not recompute expectations through the production codec or update facts from generated output. It includes implementation, regression tests, directly related documentation and affected validation as one unit. No line/time/file-count quota splits a feature mid-contract.

The M02 foundation-codec assignment uses the accepted `M02FoundationDescriptors1` and `M02FoundationKernel1` contracts in [10 section 2.1](10-binary-data-and-authoring-formats.md#21-m02-foundation-codec-contract). It may start implementation only after `M02FoundationFixtures1` has been independently derived and reviewed; pin that package's exact revision, complete byte outputs and hashes, source/materialization rules, rejection mutations and oracle/reviewer identities in the assignment. The fixture author must not use production codec/layout helpers, and the reviewer must derive the bytes independently. Tests may materialize the reviewed outputs in memory from fixed source facts; they must verify exact lengths/hashes and static semantic/status expectations without asking the codec under test to generate expected values. Do not treat the candidate values printed in [10 section 2.1 P7](10-binary-data-and-authoring-formats.md#p7-golden-vectors-and-independent-fixture-acceptance) as accepted fixtures until that review is recorded.

Private algorithms/data layouts may be chosen only within accepted contracts. Changing a public signature, schema tag, default, ownership rule, numerical behavior, unit, overflow condition, solver tolerance, callback affinity, completion boundary, or publication semantics requires a design revision before implementation continues.

Return the exact commit/revision or preserved patch; list changed paths and consequential decisions; record every validation command, profile and actual selected/executed test counts; identify failures, unsupported capabilities and remaining work. Acceptance applies only to that revision. After a correction, rerun affected checks and reconsider affected integration seams rather than relying on a prior green result.

## 3. Test and repository handoff

[29](29-project-setup-build-and-deployment.md#2-sdk-selection) owns NUnit runner/package/toolchain selection and [28](28-diagnostics-performance-and-validation.md#3-test-layers) owns validation layers. Reconcile setup commands and build-output ownership with the supplied foundation, not an assumed earlier engine repository.

Use normal `dotnet build` and `dotnet test` for implementation feedback, with focused project/filter selections and Debug before Release. Retain runner output, logs and current-run results under artifacts; optional qualification reports consume those outputs rather than rediscovering projects and running a second test workflow. Build integration belongs in MSBuild or appropriate .NET tools, not a parallel bootstrap framework. Do not run a package/publish/release matrix for every managed change; select the checks needed by the affected feature and milestone.

Use data-driven fixtures for dimensions/backends, endpoint/range edges, units/chunks, and numerical cases. Each implemented selection records fresh nonempty selected/executed counts, exits, profiles and result artifacts; reference-oracle, compiled API/layout, native, replay/fault, and measured-workload evidence remain distinguishable. An unexpectedly empty selection of implemented tests is a failure. Known empty scaffold suites are recorded as unimplemented, not as passing engine cases or a failure of unrelated implemented selections. An offline reference calculation is not an executed NUnit engine test.

## 4. Completion gates

M01 acceptance is limited to section 2.1's readiness evidence. An implementation milestone is accepted only when its public consumer examples compile without internal access or unsafe escapes; the named NUnit cases actually run; required native capabilities and failure paths are exercised; format/ownership/numerical contracts hold; and relevant integrated scenarios succeed. The exact accepted revision, test selection/execution counts, target/runtime/backend identities and artifacts are recorded.

No skipped or unexpectedly empty implemented selection, old result file, disabled case, success-shaped fallback, or unmeasured throughput target counts as success. Mock/fake-native/reference/JIT witnesses qualify only their named observations; they cannot certify the corresponding native/AOT execution. A missing hardware runner/capability is reported as a blocker with the exact unexecuted case and required capability; it is not silently omitted or marked green. Independent units may continue only when their own prerequisite revisions are accepted; do not cross the blocked case or milestone to do dependent work.

Final release acceptance includes mandatory NativeAOT runtime/editor/tool executions with generated registrations and concrete callable dispatch under a supported serviced .NET 11 profile, both graphics backends and supported desktop targets, standalone physics, custom audio/input, clean shutdown with in-flight work, binary/schema compatibility and migrations, source-format independence, spatial precision/LOD boundaries, strict replay within its admitted profile, and measured workload evidence.
