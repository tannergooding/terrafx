## 3. Exact ownership and pre-construction transaction

The following is an implementation checklist for the cited declarations, not another declaration set.

| Owner | Captured responsibility and lifetime |
|---|---|
| Entities | Freeze exact typed registrations and lower opaque roots; issue actual invocation/source/phase/frame capabilities; reserve, validate, install, revoke, and retire through the real operation. No lower signature acquires Animation/Scenes/Assets/Hosting services. |
| Animation | Own the canonical player/attachment/request algorithms and separate definition, command, playback, request-companion, and pose ownership. Root slot 0 is immutable current/previous pose/binding output; slot 1 is request-resource pin ownership. Reusable tokens are factory descriptions, not per-World owners. |
| Scenes | Own the exact activated instance/provenance/expanded-key map and pose interpretation. Prepare the real package-backed Animation dependencies alongside Rendering from one SceneExpansionPlan, with measured coexistence. No guessed authored-ID occurrence or implicit Scene activation through a Clip. |
| Rendering | Consume copied committed/restored Animation output through the selected CPU cohort. Own snapshot/palette/subdraw retention; never keep renderer-side authoritative clocks or query live ECS from native work. |
| Hosting/load preparation | Own the validated target projection, complete identity history, both typed source caches, and the exact retained package relationship. Transfer prepared assets once to the candidate; retain actual uses/credits through Read, preparation, Restore, and cleanup. |

These boundaries follow runtime ports lines 100–128, 225–350 and the typed-source addendum lines 103–245. Keep Chapter 29's existing physical and logical directions (`docs\design\29-project-setup-build-and-deployment.md:11–35`).

Pre-construction must close as one transaction:

1. **Close metadata and callable families first.** Compile exact nested descriptors; freeze Assets codecs separately. The already-proposed `AnimationSupport.CreateWorldSupportRegistration`/`WorldRegistrationBuilder.RegisterAnimationSupport` route must capture the concrete registry-specific families once, not repeatedly read replaceable factory properties. No controller constructor or Scene load performs late enlistment.
2. **Stage the whole allowed inventory on an isolated builder.** Exactly one `animation/player` persistent component; one World-scoped transferred `animation/world-state` attachment using `AnimationRuntimeState`/`AnimationRuntimeAuthor`; and resource `S("resource/animation/root-motion/v1")`, RootMotionRequest, 4096 partitions, AllowParallelAccess=false. Attachment factory is `S("attachment/animation/world-state/factory/v1")` v1; resource factory is `S("resource/animation/root-motion/factory/v1")` v1. `S` is the existing rectification assignment, not a new identity scheme. No tags, application systems, extra attachments/resources, or duplicate component registration. Validate the entire inventory before merging; rejection leaves the receiving builder mutable and unchanged.
3. **Freeze the selected graph, not just descriptors.** Require the same World's Scenes support, exact root types/families, valid resource access and complete callable dependencies. Applications get request Read only at stages 2 after the engine producer through 7; retain Build-time Write refusal and close invalid invocation-phase checks. An Animation token alone need not select rendering. The proposed CPU Animation bit requires its matching token and selected v2 render composition. Preserve the existing CPU support method's component-only rule and no-argument static composition; it is not the attachment/resource enlistment hook (`WorldRegistrationBuilder.cs:192–251`).
4. **Reserve before allocation, callbacks, or owner publication.** Fund fresh resource storage plus participant/root/control/validation/staging/cleanup backing through the actual construction plan and World/domain admission. Dynamic operations additionally fund old/current + new + scratch + retained-reader/output/pin + abort/retirement peaks. Preserve 128 MiB Animation, applicable resource/system limits, and 2 GiB World/domain constraints; count maxima promise no joint fit. A partition-size multiplication or arbitrary per-object estimate is not this closure. Use the existing construction/identity issuer, not another allocator or active-World use on an unpublished candidate.
5. **Construct fresh owners in dependency order.** Fresh lower storage → Scenes → Animation → selected CPU extraction, with the existing application-system/default initialization obligations retained. Participant reservation must equal its admitted amount. Explicitly install complete empty canonical state `(NextCommandSequence=1, Players=[])` as selected construction work, and explicitly initialize every request partition absent/zero. Registration by itself does not install an attachment; do not add an attachment Defaults callback. Construct only admitted empty owners: no package I/O, hidden player, tick, task escape, or native activation.
6. **Close both success and failure ownership.** Apply the same selection to fresh construction and restore-candidate initialization, with the candidate's actual load/construction credits. Before issuance, failures attempt every independent cleanup in reverse dependency order; refund only confirmed release and anchor unreleased ownership/credits. World shutdown joins actual participant uses before cleanup, without disposing borrowed World/Scenes/Host objects.
